# AI-2 上限复核与黄金止损执行修复

## AI-2 的请求上限

复核 `xauusd_fib_volume_pa_ai3.py:call_chat()`：主路 `https://hapiopen.cc/v1/messages`、`grok-4.7` 的实际发送结构为：

```json
{
  "model": "grok-4.7",
  "system": "独立审核规则",
  "messages": [{"role": "user", "content": "本轮实时行情和固定SL/TP"}],
  "stream": false,
  "max_tokens": 4096,
  "thinking": {"type": "disabled"}
}
```

实际请求还可能携带结构化输出 Schema；格式兼容恢复保留 `max_tokens` 和 `thinking`，每次重新提交时刷新行情。`system` 位于顶层；未在 Messages 中混用 `max_completion_tokens` 或 Chat 的 `reasoning_effort`，disabled 时也不发送 `output_config.effort`。

原生 Messages 的思考 token 也计入 max_tokens，上限参数不是只限制可见 JSON。[Claude Messages 参考](https://platform.claude.com/docs/en/api/go/messages)说明该语义；这不能证明将 Grok 转成 Messages 的第三方中转一定正确实现同样的参数。

12日18:29的实际响应报告输出7814，而实发4096且disabled，包含一个思考块，说明至少这次上游约束或计量与实发请求不一致。客户端已经拒绝该轮、暂停同配置后续付费请求；不是遗漏了上限。不能通过再加一个不属于 Messages 的上限字段、提高4096、允许残缺 JSON或忽略超限来补救。供应商是否继续计费不能由返回后的客户端保护撤销。

新增两项离线回归覆盖实际 Grok 路由的参数结构和7814超限保护。原20项请求回归仍保留。真实密钥、主备模型、档位、思考开关、超时和门槛不改，不进行付费探测。

## 现有实时护盘及发现的漏洞

实际两份 `.env` 的 `FIB_PA_POLL_SECONDS=0.5`。本地 `run_guardian()` 每次主循环读取报价、维护买单最高 Bid / 卖单最低 Ask，并用单向虚拟线、保本和真实止损护盘；AI-3按新的 M1 检查点异步分析。不能把本地护盘误说成每一分钟才更新。

原执行入口 `FibVolumePATrader.modify_position_sl()` 只与传入的持仓对象中的SL比较。这个对象可能早于同一轮另一次修改，或早于AI-3的并行修改。离线复现：旧对象仍为BUY SL95；第一次修改100.5成功；第二次提交99仍通过与95的比较，导致模拟服务器止损从100.5退回99。SELL有对应问题。这个复现不是历史日志中已经发生回退的证明，但说明原代码不能保证用户要求的“不回退”。

现已直接修复原文件的公共止损入口：

- 每次提交前按ticket重新读取唯一的当前持仓，检查symbol、magic、方向和已知identifier；未知、消失或不符即不提交。
- 与最新服务器SL比较，而不使用旧对象中的SL/TP；BUY只能提高，SELL只能降低，同价不重复请求。保留最新服务器TP。
- 读取当前Bid/Ask及point、tick_size、digits、stops_level、freeze_level，拒绝非有限值、交叉报价和缺失参数。
- 对实际提交的SL按交易tick网格向外量化，之后重新检查是否收紧及与止损触发侧的距离。
- 客户端保留 `max(stops_level, freeze_level) × point + 1 tick` 的提交距离，并检查现有SL/TP冻结及TP距离。额外一个tick是执行余量，不能当作最优策略参数或保证服务器不再拒绝。
- 不为了提交成功而把目标止损向外改松。距离不足暂缓，保留已有服务器SL。失败日志增加目标SL、当前SL/TP、Bid/Ask及经纪商距离参数。
- 黄金AI主系统原有共享 `_mt5_lock` 覆盖这次持仓读取与下单，串行化本地和AI-3的修改。仍须只运行一个实例；其它终端/程序同时修改不受本进程锁控制。

[MT5合约属性](https://www.mql5.com/en/docs/constants/environment_state/marketinfoconstants)定义stops和freeze距离。报价可能在最后检查和服务器执行之间变化，因此不能宣称消灭所有`Invalid stops`；现在至少可以定位失败的确切请求及距离。

这次修复作用于本地保本、虚拟灾难SL与AI-3 tighten的共同入口。没有修改盈利触发、缓冲、虚拟确认时间、结构退出、原SL/TP、持仓期限或入场策略，也没有把AI-3 hold改成关闭本地保护。

## 对用户提出的新分工的建议（尚未切换运行策略）

较合适的方向是“代码负责秒级执行和已锁利润，AI-3负责原交易结构的判断”，而不是默认认定AI-3所有建议都优于本地。

盈利跟踪方案应明确以下规则后再单独实施：

1. 原始SL及持仓期限始终保留；盈利保护的启动门应覆盖点差、手续费和合理回撤空间，不能刚浮盈一点就把SL贴在当前报价上。
2. 每0.5～1秒观察真实平仓侧报价，维护有利价格高水位。只有最优价格继续改善才形成新的跟踪目标；ATR下降本身不应推动新方案的保护线。
3. 目标与已经成功设置的SL均单向推进；重启以服务器现有SL为最低保护基准，保存原风险、已观察高水位和冻结规则，不根据当前策略重建原仓。
4. AI-3回复后与最新持仓、最新价和当前保护线比对。更紧且可执行的SL可采纳；较松或同价建议忽略；hold保留已锁SL；close需要按原持仓结构和有效行情执行。
5. 策略性退出主要交AI-3，代码保留原始硬止损、期限、身份与执行边界。如果要取消原本地结构退出及盈利前虚拟线，应作为明确的护盘策略变更，冻结新旧仓规则后验证，不能在这次执行修复中悄悄取消。

例如BUY入场4170、已锁SL4173：价格回撤时SL维持4173；AI建议4171不能执行，建议4173.50需要最新Bid和broker距离仍允许才执行。只有价格有利高水位继续改善时，才生成新的本地跟踪目标。SL是触发价格，不能据此保证最终平仓成交价或净利润。

近期AI-3大部分返回hold，尚无同入口、同报价成本的退出对照结果；不能由“AI会思考”推出其收益一定优于本地。下一轮退出策略验证需要逐票真实平仓回执、MFE/MAE、持仓时间和费用，本次九笔日志仍有实际净盈亏缺口。
